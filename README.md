# CS2 Predictor

Telegram-бот для неанонимных прогнозов результатов CS2-матчей в групповых чатах. Матчи и результаты синхронизируются из
PandaScore, каждый чат ведёт свои подписки, настройки, рейтинг и медали независимо от остальных.

## Возможности

- Интерфейс на HTML-разметке Telegram (жирный/курсив/моноширинный текст); навигация по меню редактирует одно и то же
  сообщение, а не плодит новые, и на каждом подэкране есть кнопка «Назад». Экраны построены по text-first принципу:
  короткий заголовок, только нужный для решения контекст, компактная клавиатура. Лёгкие действия подтверждаются
  всплывающим тостом, а не отдельным сообщением в чат.
- Администрирование ведётся в личных сообщениях с ботом: из ЛС можно управлять любым чатом, где есть права, и держать
  открытыми панели сразу нескольких чатов — каждая кнопка помнит свой чат. В группе меню открывает панель
  кнопкой-диплинком и отвечает только тому, кто его вызвал; нажатие другого участника получает всплывающее
  предупреждение (Telegram не умеет показывать сообщение только одному человеку в группе).
- Журнал изменений по каждому чату: кто и когда включил язык, часовой пояс, фильтр топ-турниров, подписался или
  отписался, назначил модератора. `Настройки → Последние изменения`.
- Копирование настроек (язык, часовой пояс, «только топ-турниры») на все чаты, которыми управляет пользователь — с
  подтверждением и списком затронутых чатов; права проверяются заново по каждому чату в момент применения.
- Личные уведомления, строго по подписке и выключенные по умолчанию: напоминание о незакрытом голосовании и разбор
  собственного результата после матча.
- Персональный разбор: текущая и лучшая серии, форма за последние 10 прогнозов, точность по командам, динамика за 30
  дней против предыдущих 30.
- Своё имя в списках результатов: `Моя статистика → ✏️ Моё имя в списках` задаёт имя для рейтингов, дайджестов и годовых
  номинаций отдельно от имени в Telegram-профиле; голосования его не меняют, сброс — той же кнопкой.
- Уборка завершённых турниров из подписок одной кнопкой с подтверждением; активные турниры в списке всегда выше
  завершённых.
- Поиск турниров PandaScore и подписка через Telegram UI; турниры отмечены значком уровня (S — 🌟, A — ⭐, B — 🔹).
  `/events top <запрос>` ищет только среди S/A, `/events all <запрос>` — среди всех уровней; в настройках чата можно
  выбрать поведение по умолчанию для `/events <запрос>` без явного `top`/`all`.
- При появлении в каталоге нового турнира S/A уровня бот сам предлагает его добавить: сообщение с кнопкой «Подписаться»
  уходит во все активные чаты, ещё не подписанные на этот турнир.
- Автоматическая отправка всех будущих матчей после определения обеих команд.
- Нативные неанонимные опросы: BO1, BO2, BO3, BO5, произвольные `best-of`, `fixed-maps`, `first-to`; вопрос дополняется
  хэштегами турнира и команд для поиска по истории чата.
- Закрытие опроса по расписанию или сразу при статусе матча `running`.
- Перенос дедлайна при переносе матча, аннулирование при отмене или технической победе.
- Идемпотентная обработка изменённых голосов, повторных webhook update и результатов.
- Рейтинги за месяц, год, турнир и всё время в часовом поясе чата.
- Автодайджест в 20:00 по часовому поясу чата: в последний день месяца — Top-3 месяца и промежуточный Top-3 года; 31
  декабря — Top-3 декабря, итоговый Top-3 года и шесть годовых номинаций. Полный рейтинг в дайджест не входит, он
  открывается кнопкой «Весь год». Доставка идемпотентна (PostgreSQL + transactional outbox), окно восстановления — до
  06:00 следующего дня.
- Плотное ранжирование, динамика мест, очки за последний матч, золотые/серебряные/бронзовые медали.
- Русская и английская локализации; язык интерфейса в ЛС не зависит от языка группы.
- Обогащение данных о командах (Valve Regional Standings, опционально GRID и Liquipedia) — только как дополнительный
  контекст в опросе. Источник истины по событиям, матчам и результатам один — PandaScore.
- Telegram Topics: общая тема чата и переопределение для конкретного турнира.
- Администраторы Telegram и назначаемые ими модераторы.
- Транзакционный outbox, PostgreSQL advisory locks, структурированные логи, health checks, Prometheus-метрики.
- Синхронизация с PandaScore глобальная и по расписанию, не зависит от числа чатов: опросы и уведомления собираются из
  уже сохранённого в PostgreSQL каталога, ни одна команда пользователя не порождает новый вызов PandaScore.
- Провайдеры данных о турнирах — сменный список с fallback на следующий провайдер, индикатором staleness и circuit
  breaker (после серии отказов подряд провайдер временно исключается из вызовов, интервал отключения растёт
  экспоненциально). Сейчас настроен один провайдер, PandaScore; добавление ещё одного не требует изменений в
  бизнес-логике.
- Каждый плановый job (синхронизация, закрытие опросов, outbox) ограничен таймаутом, зависший вызов не держит соединение
  с БД бесконечно.
- Rate limiting на `/telegram/webhook` (token bucket) поверх проверки секретного токена.
- Исходящие вызовы Bot API притормаживаются под лимиты Telegram — общий бюджет и отдельно на чат, а не только реакция на
  429 постфактум.
- Retention-джоба чистит таблицы, растущие вместе с трафиком: журнал дедупликации webhook'ов, опубликованные строки
  outbox, закрытые запросы на подтверждение, журнал изменений. У каждой таблицы свой TTL.

Ссылки на hltv.org бот не публикует: PandaScore не отдаёт HLTV ID, а условия HLTV запрещают scraping, так что любая
привязка была бы ненадёжной. Опрос и статистика строятся на данных PandaScore и локальном PostgreSQL-кэше. Для команд
сохраняется доступный PandaScore country/location, но флаг страны не выводится в основном интерфейсе; в опросе кратко
указывается баланс побед/поражений команды в текущем турнире по уже закэшированным завершённым матчам. Букмекерские
коэффициенты не входят в PandaScore Statistics API — нужен отдельный PandaScore Odds product, поэтому без доступа к нему
бот коэффициенты не показывает.

## UX/UI принципы

- **Text-first.** Emoji не используются как префиксы меню, настроек, времени, метрик и навигации. Иерархия строится
  заголовками, переносами строк, короткими подписями и порядком кнопок.
- **Emoji только по смыслу.** Emoji остаются там, где несут отдельную информацию и ускоряют сканирование: уровень
  турнира (`🌟` S, `⭐` A, `🔹` B), медали Top-3 (`🥇🥈🥉`), отдельные критичные состояния в уведомлениях.
- **Постепенное раскрытие.** Длинный список — для выбора объекта, не для показа всех его действий. В «Моих турнирах»
  одна кнопка соответствует одному турниру; статистика, отписка и привязка Topic доступны на карточке выбранного
  турнира.
- **Одно значение — одно место.** Текущее значение настройки показано прямо в кнопке (`Язык: Русский`,
  `Часовой пояс: Europe/Moscow`, `Турниры: только S/A`), а не дублируется отдельной строкой над клавиатурой.
- **Состояние — это результат.** Вместо абстрактного «вкл/выкл» интерфейс называет, что именно включено
  (`Турниры: только S/A` / `Турниры: все`, `Итоги матчей: включены` / `выключены`).
- **Плотность под задачу.** Рейтинг отвечает на вопрос «кто выше и сколько очков», ближайшие матчи — «что играет
  следующим», персональный экран — «как выступаю я». Второстепенные данные — на более глубоких экранах.
- **Группировка расписания.** Берутся десять ближайших матчей, объединяются по турнирам и датам в часовом поясе чата:
  турниры идут по времени первого матча, внутри даты — по времени начала. Название турнира и дата показаны один раз, у
  матча остаются время, команды, формат и стадия.

## Стек

Go 1.27, PostgreSQL 17, [pgx](https://github.com/jackc/pgx) без ORM, [goose](https://github.com/pressly/goose) для
миграций, стандартный
`net/http`, [Prometheus client_golang](https://github.com/prometheus/client_golang), [testcontainers-go](https://github.com/testcontainers/testcontainers-go)
для интеграционных тестов.

Приложение собирается через Docker и shell. Для установки на сервер используются Ansible и Python на runner; подробности
в разделе «Деплой».

## Архитектура

Гексагональная организация без DI-фреймворка, сборка вручную в `cmd/bot/main.go`.

```text
cmd/bot                      composition root (main.go)
internal/domain/competition  события, команды, матчи, серийные форматы, счёт
internal/domain/chat         настройки чатов, Topics, авторизация
internal/domain/subscription подписки чатов на турниры
internal/domain/prediction   опросы и изменяемые голоса
internal/domain/scoring      начисления, dense ranking, рейтинг, медали
internal/platform/common     общие идентификаторы и инфраструктурные порты
internal/adapter/postgres    реализации портов на pgx + миграции (goose)
internal/adapter/pandascore  внешний каталог турниров и матчей
internal/adapter/telegram    webhook, Bot API клиент, i18n, локализованный UI
internal/app                 планировщик, outbox-диспетчер, метрики
internal/app/httpapi         HTTP-роутер, middleware, health/version-эндпоинты
docker                       Dockerfile и Compose-манифесты (dev и production)
```

Пакеты `internal/domain/*` не зависят ни от адаптеров, ни от `internal/app`; граница проверяется тестом на графе
импортов (`go list -deps`). Межмодульные вызовы идут через интерфейсы, внешние уведомления — через transactional outbox.

## Запуск

Нужен Docker либо Go 1.27+ и PostgreSQL 17.

```bash
cp .env.example .env
# заполнить TELEGRAM_BOT_TOKEN, TELEGRAM_WEBHOOK_SECRET и PANDASCORE_TOKEN
make up
```

`make up` поднимает `docker/compose.yml` — PostgreSQL и бот, собранный из рабочего дерева. Бот слушает `127.0.0.1:8080`;
ни публичного имени, ни сертификата локально не нужно. `make logs` показывает логи, `make down`
останавливает стек и удаляет его volumes.

Production-стек описан отдельно в `docker/compose.prod.yml`: тот же бот, но из опубликованного образа и за Caddy,
который получает сертификат Let's Encrypt и проксирует только три пути. Как он устанавливается на сервер — в разделе
«Деплой» ниже.

Локальный запуск без Docker, против своей базы:

```bash
go run ./cmd/bot
```

Telegram не может доставлять обновления на `localhost`, поэтому для работы с живым ботом нужен публичный HTTPS-адрес.
Webhook регистрируется один раз:

```bash
curl -X POST "https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/setWebhook" \
  -d "url=https://your-host.example/telegram/webhook" \
  -d "secret_token=${TELEGRAM_WEBHOOK_SECRET}" \
  -d 'allowed_updates=["message","callback_query","poll_answer","my_chat_member"]'
```

Проверка регистрации: `curl "https://api.telegram.org/bot${TELEGRAM_BOT_TOKEN}/getWebhookInfo"`. На production-сервере
это делается один раз, при первой установке — сама установка (см. «Деплой») меняет только код и контейнеры, URL webhook
от релиза к релизу не меняется.

Без обязательных секретов приложение не запускается. PandaScore token не должен передаваться в клиентские приложения.

### Конфигурация

Все параметры — переменные окружения, с значениями по умолчанию в `internal/app/config.go`. Обязательные секреты:
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `PANDASCORE_TOKEN`. Остальное опционально: задержки синхронизации,
таймауты HTTP-клиента, порядок и health-пороги провайдеров, размер батча outbox. Каталог событий обновляется раз в час
(`SYNC_EVENTS_DELAY_MS=3600000`), матчи активных подписок — раз в 3 минуты (`SYNC_MATCHES_DELAY_MS=180000`), проверка
времени monthly/yearly-дайджеста — раз в минуту (`DIGEST_CHECK_DELAY_MS=60000`).

## Команды

- `/menu` — главное меню.
- `/events Cologne` — поиск турнира, подписка кнопкой. `/events top Cologne` ищет только среди S/A уровня,
  `/events all Cologne` — среди всех уровней (переопределяет настройку чата по умолчанию). Команда не обязательна:
  `Меню → Турниры → Добавить турнир → Поиск по названию` отправляет ForceReply, и достаточно ответить частью названия.
  Турниры, уже добавленные в чат, из каталога и поиска исключаются.
- `/stats` в групповом чате открывает меню статистики: последний доступный месяц и год, «Всё время», статистика по
  турнирам, выбор другого периода. Рейтинг показывает место, имя и очки без повторяющихся подробностей у каждого
  участника.
- В личном чате с ботом `/start`, `/menu` и `/stats` открывают персональную статистику по всем группам, где пользователь
  голосовал: всё время, год, месяц, детализация по каждому чату. Голосования в разных чатах считаются отдельными
  участиями; один и тот же турнир в общей персональной статистике учитывается один раз.
- В конце каждого месяца бот публикует Top-3 месяца и текущий Top-3 года. 31 декабря в 20:00 — Top-3 декабря, итоговый
  Top-3 года и номинации: 🚀 камбэк года, 🎯 снайпер года, 🧠 эксперт года, 💎 точный расчёт, 🔥 серия года, 🤝 талисман
  команды. Полный список участников в годовой автодайджест не входит, он доступен кнопкой годовой статистики.
- `/timezone Europe/Moscow` меняет часовой пояс чата, только для менеджера. Из UI: `Настройки → Часовой пояс` — восемь
  популярных зон в один тап, текущая отмечена; команда остаётся для остальных случаев.
- `/topic here` привязывает текущую Topic по умолчанию, только для менеджера.
- `Настройки → Модераторы` показывает назначенных модераторов. Администратор или уже назначенный модератор назначает
  других командой `/moderator add` ответом на сообщение участника; `/moderator remove` снимает роль. Статистика доступна
  всем участникам чата без роли менеджера.
- В ЛС `Моя статистика → Уведомления` — переключатели личных напоминаний и разборов, по умолчанию выключены, та же
  кнопка выключает обратно. `Моя статистика → Разбор` — серии, форма, точность по командам, динамика.
  `Моя статистика → ✏️ Моё имя в списках` — своё имя для рейтингов и дайджестов, кнопка сброса возвращает имя из
  Telegram-профиля.
- Отписка от турнира требует подтверждения «второй руки»: если есть другой действующий администратор или модератор,
  удаление подтверждает он. Если второго управляющего нет — или до него нельзя достучаться в ЛС, Telegram не даёт боту
  написать первым тому, кто с ним не начинал диалог, — инициатор подтверждает действие сам повторно. Пока запрос ждёт
  вторую подпись, его можно отозвать; тем, кого уже спросили, придёт уведомление об отзыве. Массовая уборка завершённых
  турниров подтверждения второй руки не требует — у завершённого турнира нет опросов, которые можно было бы тихо
  остановить.

## Makefile

`make help` выводит список всех целей. Основные:

```bash
make build             # собрать бинарник в bin/
make run               # запустить локально, подхватив .env
make test              # unit-тесты
make test-integration  # интеграционный тест (реальный Postgres через testcontainers-go, нужен Docker)
make check             # fmt-check + vet + lint + test — то же, что гоняет CI (без integration/docker)
make cover             # unit-тесты с покрытием, отчёт в coverage.html
make up / make down    # поднять/остановить локальный стек (postgres+bot)
make lint              # golangci-lint (скачивается по требованию, глобальная установка не нужна)
```

## Тесты

```bash
go vet ./...
go test ./...
go test -tags integration ./...   # интеграционный тест с реальным Postgres через testcontainers-go
```

Тесты покрывают бизнес-правила форматов и начислений, изменение голосов, права, плотное ранжирование, маппинг
PandaScore, retry-логику Telegram-клиента (429 с учётом `retry_after`), оркестрацию settlement/event-completion,
advisory locks (реальная взаимная блокировка на Postgres), idempotency claim/release, soft-delete подписок и границы
модулей. Интеграционные тесты поднимают PostgreSQL 17 через testcontainers-go, применяют все миграции (goose) и
проверяют полный путь `опрос → голос → начисление → рейтинг → медаль`.

`golangci-lint` (конфиг — `.golangci.yml`) поверх стандартного набора гоняет `gosec`, `bodyclose`, `unconvert`,
`unparam`, `misspell`.

## Наблюдаемость

- `GET /healthz/live` — процесс жив.
- `GET /healthz/ready` — проверяет доступность БД (`Ping`) и статус провайдеров данных (свежесть последнего успешного
  вызова); `503`, если БД недоступна или провайдеры давно не отвечали.
- `GET /metrics` — метрики Prometheus: `competition_sync_runs_total`, `competition_sync_entities`,
  `competition_provider_calls_total` (включая `circuit_open`, когда вызов пропущен из-за открытого circuit breaker),
  `competition_provider_latency_seconds`, `prediction_polls_total`, `outbox_events_total`, `http_requests_total`,
  `http_request_duration_seconds`, `http_panics_recovered_total` (по HTTP-эндпоинтам под middleware — сейчас webhook).
- `GET /version` — версия/коммит/время сборки, подставляются через `-ldflags` в `make build`/`docker build`; локальный
  `go run` покажет `dev`/`unknown`.
- Docker `HEALTHCHECK` и healthcheck в `docker/compose.yml` опрашивают `/healthz/live`; production-стек ждёт
  `/healthz/ready`, потому что установка должна знать, что миграции прошли и база отвечает, а не только что процесс
  стартовал.
- Структурированные JSON-логи в stdout (`log/slog`).
- Секреты и Telegram token не логируются: ошибки транспортного уровня в Telegram-клиенте никогда не содержат текст
  исходной ошибки (в нём может быть URL с токеном), только описание от самого Telegram API.
- Graceful shutdown: по SIGINT/SIGTERM сервер сначала перестаёт принимать новые запросы, дожидается завершения фоновых
  job (sync/outbox) и только потом закрывает пул БД, так что job не упирается в уже закрытое соединение.
- 429 от Telegram Bot API ретраится автоматически, до 3 попыток, с учётом `retry_after`, capped на 30 секунд; ретраится
  только явный 429, не транспортные таймауты, поэтому отправка не задваивается.

Миграции лежат в `internal/adapter/postgres/migrations/`, применяются через goose при старте приложения, каждая — в
своей транзакции.

## Сборка образа

```bash
make docker-build   # linux/amd64 — единственная архитектура, под которую публикуется образ
```

`docker/Dockerfile` требует BuildKit: он использует `RUN --mount` для кэшей Go и для необязательного build secret. В
Docker Desktop и на runner'ах GitHub buildx есть из коробки; при установке через Colima или отдельный Docker Engine
плагин ставится отдельно (`brew install docker-buildx` на macOS), иначе сборка откатится на классический builder и не
поймёт `RUN --mount`.

Секреты в сборку передаются только через `--secret`, никогда через `ARG` или
`ENV`: и то и другое попадает в историю образа и остаётся читаемым для всех, кто может его скачать. Сейчас ни одна
зависимость проекта не требует авторизации; если появится приватный модуль, механизм уже на месте:

```bash
docker buildx build --secret id=netrc,src="$HOME/.netrc" -f docker/Dockerfile .
```

Файл монтируется в tmpfs внутрь одного `RUN` и исчезает вместе с ним, не становясь частью слоя. Без флага mount просто
отсутствует, и сборка идёт как обычно.

В образ попадает только то, что перечислено в `COPY`: `cmd/` и `internal/`. Никакого `COPY . .` — что уходит в слой,
решает сам Dockerfile, а не то, подхватился ли файл исключений. `docker/Dockerfile.dockerignore` дополнительно сокращает
контекст и написан как allow-list, чтобы новый файл в рабочем каталоге по умолчанию в него не попадал.

## Деплой

После merge в `main` workflow `release.yml` публикует образ в GHCR и создаёт релизный тег. Установка запускается вручную
через `deploy.yml` с тегом
`vMAJOR.MINOR.PATCH`.

Деплой реализован в репозитории через Ansible: runner берёт автоматизацию из основной ветки, конфигурацию
Compose/Caddy — из выбранного тега, определяет digest образа в GHCR, проверяет его подпись (`cosign`, keyless — образ
подписывается в `release.yml` тем же workflow, никакого ключа подписи не существует) и передаёт конфигурацию серверу.
Git checkout на сервере не нужен. Перед изменениями Ansible создаёт и проверяет резервную копию текущей конфигурации;
ошибка backup останавливает деплой. Затем запускает production Compose и ждёт health checks — при неудачном health
check автоматически откатывается на предыдущий образ.

Ansible подключается к уже подготовленной VM пользователем из `DEPLOY_USER`
(`cs2deploy`) по ключу `DEPLOY_KEY` и использует passwordless `sudo`, но не до
root — только до `APP_USER` (`cs2predictor`): деплою реальный root не нужен
нигде, см. `ansible/README.md` → «Least-privilege deploy». Первичная
инициализация VM выполняется отдельно от репозитория:
к моменту первого деплоя должны существовать `cs2deploy`, `cs2predictor`,
`/opt/cs2predictor`, Python 3, Docker Engine + Compose и SSH-доступ на настроенном порту. `preflight.yml` проверяет SSH,
sudo, Python и Docker фиксированной командой без выполнения кода из PR.

Если сервер изначально был подготовлен под более раннюю, ограниченную модель доступа (ключ `cs2deploy` с `ForceCommand`,
без generic sudo), его нужно мигрировать один раз — `ansible/bootstrap.yml` (роль `host_access`), запускается вручную от
`admin`. Подробности: [ansible/README.md](ansible/README.md#host-access-migration).

Регистрация Telegram webhook — отдельная ручная и необязательная джоба,
`.github/workflows/webhook.yml` (`ansible/webhook.yml`): она нужна после установки релиза, который меняет
`TELEGRAM_WEBHOOK_SECRET` или `CADDY_DOMAIN`
(в первую очередь — самая первая установка), а не после каждого деплоя. Токен и секрет читаются из серверного `.env` и
через GitHub Actions не проходят.

При падении `deploy.yml` бот сам уведомляет своих администраторов в личные сообщения — список Telegram ID задаётся
опциональной переменной `DEPLOY_NOTIFY_CHAT_IDS` в GitHub environment `production` (через
запятую; пробелы после запятой допустимы, каждый ID обрезается). Без этой
переменной уведомление тихо не отправляется — сервер даже не проверяется на наличие `.env`; при успешном деплое оно не
отправляется никогда.

В GitHub environment `production` обязательны variable `DEPLOY_HOST` и secrets
`DEPLOY_KEY`, `KNOWN_HOSTS`. Стандартные значения уже совпадают с bootstrap VM:
`DEPLOY_PORT=22`, `DEPLOY_USER=cs2deploy`, `APP_USER=cs2predictor`,
`APP_PATH=/opt/cs2predictor`; одноимённые GitHub variables нужны только для override. Серверный `<APP_PATH>/.env`
собирается самим `deploy.yml` из пяти отдельных значений production environment при каждом деплое (владелец
`APP_USER`, права `0600`) — вручную его создавать не нужно, и деплой не может пройти, если хоть одно не задано:
secrets `POSTGRES_PASSWORD`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `PANDASCORE_TOKEN` и variable
`CADDY_DOMAIN`. Подробности: [ansible/README.md](ansible/README.md#server-environment-file).

Параметры inventory, требования к подготовленной VM, состав backup и порядок
восстановления: [ansible/README.md](ansible/README.md). Backup сохраняет конфигурацию, но не данные PostgreSQL;
автоматического отката миграций и контейнеров нет.
